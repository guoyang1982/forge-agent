# Forge 产品与工程路线图

> 状态：长期维护中的方向性路线图
> 最近更新：2026-08-27
> 说明：本文定义“值得陆续建设什么、为什么值得做、完成后如何判断有效”。它不承诺具体发布日期；进入开发前，每项功能仍需独立规格、实施计划和验收。

## 1. 路线图目标

Forge 的长期方向不是继续堆叠模型、工具和人才数量，而是形成一条可验证的产品链路：

```text
可靠执行
  → 有依据地回答
  → 沉淀为可复用资产
  → 多专家跨工作区安全协作
  → 接入真实系统并持续运行
  → 用评测和业务数据判断效果
  → 在受控条件下持续改进
```

最终希望用户获得五种能力：

1. **放心交付任务**：能看见过程、验证结果、定位失败并回滚。
2. **积累 AI 资产**：把 SOP 沉淀为 Skill、知识库、专家、团队和自动化。
3. **组建真正的 AI 团队**：不同专家在不同工作区并行工作，由负责人统一协调和验收。
4. **连接真实业务系统**：通过受控连接器读取数据、执行动作，并由事件或计划持续触发。
5. **越用越好但不失控**：从失败中产生评测和候选改进，所有变更可审计、可验证、可回滚。

## 2. 路线图原则

- **本地优先**：工作区、会话和敏感数据默认留在用户控制的设备或主机上。
- **先验证，再扩展**：没有评测、Trace 和回滚能力的功能，不进入自动进化阶段。
- **共享资产，隔离执行**：团队可以共享专家定义、Skill 和知识，但代码、凭证、个人记忆和临时状态按工作区隔离。
- **每个写入边界只有一个负责人**：不同工作区可并行写入；同一工作区同一时刻保持 single-writer。
- **确定性验证优先**：测试、编译、文件状态和业务环境结果优先于 LLM 自评。
- **质量优先于数量**：活跃率、成功率和节省时间比模板数、代码行数和运行次数更重要。
- **高影响操作可控**：外部写入、凭证、部署、删除和不可逆操作必须经过权限、审计和必要确认。
- **渐进交付**：先交付可独立产生价值的最小闭环，再扩展自动化和生态。

## 3. 已有基础

以下能力已经存在，路线图应在它们之上增强，不重复建设：

- 自研 Forge Agent Runtime、ReAct 循环、计划、工具调用、Reflection 和检查点回滚。
- 持久化 `AgentEvent` 时间线、工具状态、文件变更、人才派活和上下文用量事件。
- `pnpm eval` 轻量评测入口和隔离临时环境，但尚未形成完整任务数据集与指标体系。
- 手动 `/compact` 会话压缩和上下文上限提醒。
- 基础长期记忆、项目记忆和人才运行记忆。
- Skills、插件、MCP、Hooks、Extension Hub 和多 Runtime 分发。
- Talent Package v2、248 个职业模板、人才团队、波次编排和后台人才只读机制。
- Cron/手动自动化、独立 Session、运行历史与通知配置。
- PDF、Office 文档和文本附件提取能力，可作为知识库摄取基础。
- Desktop、CLI、Mobile、Channel Gateway 和远程主机访问能力。

## 4. 优先级与状态

### 优先级

| 优先级 | 含义 |
|---|---|
| **P0** | 质量与架构地基，其他能力依赖它，应优先规划。 |
| **P1** | 能直接提升用户价值、团队复用或企业落地能力。 |
| **P2** | 有长期价值，但必须等待评测、权限或治理能力成熟。 |
| **条件型** | 仅在有明确用户需求、客户场景或数据证明时投入。 |

### 状态

| 状态 | 含义 |
|---|---|
| **候选** | 已确认有价值，尚未形成独立规格。 |
| **已设计** | 已有经过确认的设计文档和边界。 |
| **开发中** | 已进入实施计划并开始开发。 |
| **已交付** | 已通过验收，转入正式产品文档维护。 |
| **暂缓** | 价值成立，但当前依赖、成本或风险不允许继续。 |

除“已有基础”外，本文中的新增项目默认状态为 **候选**。状态变化时应附设计、计划或交付文档链接。

## 6. 近期：先建立质量闭环

### R1. Agent 评测中心

在现有 `pnpm eval` 基础上，建设正式评测运行器和任务规范。

要做：

- 定义任务数据格式：初始工作区、用户请求、允许工具、环境重置、验证器、标签和预算。
- 建立正常路径、模糊需求、权限、提示注入、工具失败、恢复和长任务用例。
- 支持同一任务重复运行，报告成功率和不稳定性。
- 记录任务成功、工具正确性、权限合规、延迟、Token 和成本。
- 支持模型、Prompt、Skill、Harness 组件的成对比较和消融。
- 为关键能力建立 CI 回归门，不要求所有实验型用例阻断发布。

完成标准：

- 核心评测集至少覆盖编码、只读分析、人才协作、记忆、自动化和安全边界。
- 每个核心用例都有确定性结果验证；LLM Rubric 只用于无法完全程序化的质量维度。
- 关键版本变更可以生成可比较报告，并识别偶发失败。

### R2. Trace、Span 与任务回放

把现有扁平事件流升级为可关联的运行树。

要做：

- 引入 `runId`、`turnId`、`spanId`、`parentSpanId` 和统一时间戳。
- 记录 LLM、工具、检索、人才、验证和自动化 Span。
- 补充模型、Prompt、Skill、工具版本、Token、成本、重试和结果摘要。
- 原始长输出落到受控产物文件，Trace 只保存摘要、哈希和路径。
- 支持从失败 Span 重新运行单步或生成回归用例。
- 对敏感参数、凭证和用户数据进行结构化脱敏。

完成标准：

- 任意失败任务可以定位到明确步骤和错误类别。
- Desktop 重启后仍能恢复调用树、状态、耗时和证据。
- Trace 不成为新的敏感数据泄漏面。

### R3. 三层自动验证

每次交付分别检查：

1. **结果层**：文件、测试、数据库或外部系统状态是否达到目标。
2. **过程层**：是否使用允许的工具、遵守权限、完成必要验证、没有越界副作用。
3. **回答层**：最终回答是否完整、与真实执行结果一致、没有虚构。

要做：

- 为代码任务接入定向测试、编译、Lint、Diff 和声明一致性检查。
- 为工具任务验证最终环境状态，而不是只检查模型文本。
- 让 Reflection 消费结构化 Trace 和验证结果，而不只消费错误摘要。
- 对高风险任务支持独立验证者读取原始证据。

完成标准：

- Agent 不能在关键验证失败时宣称任务完成。
- 每个自动重试和返工路径都有次数与时间上限。

### R4-R5. 动态状态栏与自适应压缩

要做：

- 保持稳定 System Prompt，把分支、计划、工具次数、失败、剩余预算等动态信息追加到上下文尾部。
- 状态栏包含当前工作区、修改文件、测试状态、TODO、重试次数和上下文占用。
- 达到阈值后自动压缩；支持工具结果预算、噪声删除、阶段摘要和完整模型压缩。
- 保留架构决策、约束、路径、标识符、测试结果、未完成事项和回滚说明。
- 为压缩增加失败降级和熔断，禁止无限调用模型压缩模型输出。

完成标准：

- 长任务后半程的重复调用和目标遗忘下降。
- 压缩前后关键路径、错误、验证状态和 TODO 保持准确。

## 7. 近期至中期：知识、记忆与资产

### R6. 一等公民知识库

知识库负责“当前事实和业务口径”，与负责“怎样做”的 Skill、负责“执行动作”的工具和负责“协作经验”的 Memory 分离。

要做：

- 支持本地目录、文档附件和连接器数据源。
- 支持增量同步、版本、删除传播、作用域和访问权限。
- 支持文本切分、混合检索、重排、引用和原文定位。
- 内置检索测试、问答测试、覆盖率和引用正确性评测。
- 一个知识库可挂多个专家，更新后无需重新发布 Skill。
- 复用现有 `document-extract` 作为文档摄取起点，扫描版 PDF 的 OCR 作为独立扩展。

完成标准：

- 回答能够显示来源、版本和定位信息。
- 未检索到依据时，专家明确说明不确定性，不编造业务事实。

### R7. 记忆中心 2.0

要做：

- 写入流程采用候选 → 判断 → ADD/UPDATE/DELETE/NOOP → 可信记忆。
- 增加来源、证据、置信度、重要性、创建时间、有效期、失效原因和访问记录。
- 支持个人、个人×项目、个人×专家、专家×项目和团队×项目作用域。
- 提供查看、搜索、编辑、删除、固定、禁用和“本次为何召回”界面。
- 默认不把原始跨用户对话写入专家共享记忆；只允许脱敏、验证后的通用经验。
- 引入冲突检测、版本和陈旧记忆降权。

完成标准：

- 用户能纠正任意影响行为的长期记忆。
- 陈旧或低置信记忆不会静默覆盖当前项目事实。

### R8、R10-R13. AI 资产产品化

统一资产链：

```text
业务 SOP → Skill → 知识库/工具 → 专家 → 团队 → 自动化 → 运行数据 → 优化
```

要做：

- 为 Skill、知识库、专家、团队和自动化统一版本、Owner、来源、依赖和兼容性信息。
- 支持草稿、测试、审核、发布、启用、弃用和回滚。
- 发布前运行说明完整性、安全、权限、依赖和评测检查。
- 建立 L1-L4 引导：找专家 → 教会专家 → 组团队/连系统 → 自动化/记忆。
- 识别重复任务并建议沉淀，但保存前必须由用户确认。
- 从“增加模板数量”转向少量旗舰专家包，优先发布发布审查、故障排查、需求交付和跨仓库研发等真实闭环。

完成标准：

- 一个资产可以导入、复制、升级、审计和回滚。
- 可以查询某次运行实际使用了哪些资产版本。
- 旗舰专家有真实评测和明确验收标准，不以人设文本长度判断质量。

## 8. 中期重点：多工作区专家团队编排

### R9. 目标

一次团队任务可以绑定多个工作区。每个专家拥有明确工作区、工具、权限和写入边界；不同工作区可并行写入，同一工作区同一时刻只有一个写入负责人。

典型工作区组：

```text
产品团队任务
├── requirements     产品与验收标准
├── web-frontend     Web 前端仓库
├── backend-api      后端仓库
├── mobile-app       移动端仓库
├── infrastructure   部署与基础设施
└── integration      跨仓库验证
```

### R9.1 工作区组与绑定

要做：

- 新增 `WorkspaceGroup`，管理多个本地目录、仓库或临时沙盒。
- Session 从单一 `cwd` 扩展为主工作区加多个受控工作区引用。
- 人才可配置默认工作区、允许工作区、读写策略、分支策略、构建和测试命令。
- 用户可以在任务中临时覆盖人才工作区，但模型不能自行扩大权限。
- 新工作区只能通过受控创建流程产生，记录 Owner、来源、用途、权限和生命周期。

### R9.2 并行与写入安全

- 不同工作区允许不同专家并行写入，各自拥有独立锁、检查点和验证。
- 同一仓库的并行开发使用独立 Git Worktree 或隔离沙盒。
- 同一工作区默认 single-writer；所有权通过显式交接转移。
- `run_command` 产生的文件副作用纳入工作区归属、审计和完成后 Diff 检查。
- 任一专家失败不能自动撤销其他工作区已完成且通过验证的产出。

### R9.3 结构化交付和产物总线

专家之间只交接必要信息：

- 结论和置信度。
- 修改文件、分支、Patch 或提交引用。
- 测试命令和结果。
- API、Schema、设计稿、报告等版本化产物。
- 未解决风险和对后续任务的约束。

统一产物记录来源工作区、生成者、版本、哈希、可见范围和验证状态。主上下文不复制每个专家的完整探索轨迹。

### R9.4 跨工作区编排与验收

- RunPlan 扩展 `workspaceId`、产物依赖和跨工作区 DAG。
- 无依赖工作区并行，有契约依赖的步骤按波次执行。
- API 或 Schema 变化触发依赖工作区重新验证。
- 增加集成工作区或 CI 验证跨仓库组合结果。
- 团队看板展示专家、工作区、分支、状态、Diff、验证和阻塞关系。

### R9 MVP 完成标准

1. 一个工作区组可以注册至少两个工作区并绑定不同人才。
2. 两名专家可以在不同工作区并行修改和验证，不互相获得凭证或写权限。
3. 团队负责人能看到每个工作区的修改、测试、风险和交付物。
4. 同一工作区的并发写被拒绝、排队或隔离到 Worktree。
5. 跨工作区任务支持依赖、失败恢复、取消和最终集成验收。

## 9. 中期：连接器、自动化与异步协作

### R14. 连接器治理中心

要做：

- 统一连接器目录、Owner、适用范围、认证方式、权限、版本和健康状态。
- 凭证以安全引用方式注入工具，默认不进入模型上下文和 Trace。
- 记录哪些 Skill、专家、团队和自动化依赖连接器。
- 提供只读/写入能力声明、验收用例、调用审计、错误率和撤销流程。
- 对敏感系统支持网关、最小权限、服务身份和高风险操作确认。

完成标准：

- 管理员可以撤销单项能力或凭证，而不必删除整个专家。
- 连接器升级后能够自动运行兼容性评测。

### R15. Automation 2.0

要做：

- 在 Cron/手动触发之外增加签名 HTTP/Webhook 和业务事件触发。
- 定义输入 Schema、事件过滤、幂等键、并发策略、超时和取消。
- 支持重试、退避、死信、补偿动作和人工接管。
- 自动化使用专属服务身份，不能静默继承创建者全部个人权限。
- 支持成功/失败通知、持续会话、运行历史和一键转人工任务。
- 让专家团队和多工作区任务成为自动化执行目标。

完成标准：

- 重复事件不会造成重复副作用。
- 自动化失败可以定位、重试、接管和回放。
- 权限、成本和运行数据可按自动化单独统计。

### R16. 统一审批与通知中心

集中展示：

- 等待确认的命令、网络、连接器和外部写入。
- 自动化失败、预算超限和需要人工接管的任务。
- 多工作区合并、部署和删除等高影响操作。
- 已完成任务和用户订阅的结果通知。

审批应绑定具体操作摘要、作用域、身份和过期时间，禁止使用含糊的长期全局授权。

## 10. 中期：效率、成本与运营

### R17. 多 Agent 结构化交接

- 子任务必须包含目标、验收条件、工作区、允许工具和预算。
- 返回结果必须包含结论、证据位置、产物、不确定项和建议动作。
- 独立验证者读取原始证据和结论，不继承前一个 Agent 的完整推理。
- 只有能产生新信息或真正并行的任务才启用多 Agent。

### R18. 智能模型路由与预算

- 按任务类型、复杂度、风险、上下文长度和工具需求选择模型。
- 对任务、子 Agent、团队和自动化设置调用、Token、成本和时间预算。
- 支持预算不足时降级、减少并行、请求确认或停止，而不是无限继续。
- 用评测数据验证路由策略，不按模型品牌硬编码质量假设。

### R19. 工具渐进式发现

- 默认只提供核心工具和精简能力目录。
- 按 server → tool 或 Skill → dependency 分层发现工具。
- 需要调用时才加载完整参数 Schema、成本和副作用说明。
- 工具说明包含使用时机、边界、反例、参数示例、返回值、幂等性和费用。

### R20. 业务效果与 ROI 看板

重点指标：

- 任务成功率、稳定性和人工接管率。
- 首次成功时间、完成耗时和节省时间。
- 测试通过率、返工率和回滚率。
- Skill、专家、团队和自动化的活跃率与复用率。
- 自动化成功率、重复事件率和平均恢复时间。
- 单次成功任务的 Token、模型、工具和基础设施成本。
- 权限拒绝、越权拦截、敏感信息拦截和安全事件。

模板数、代码行数、提交数和运行次数只能作为规模信息，不能单独证明收益。

## 11. 远期：持续改进与生态

### R21. 失败轨迹转回归用例

- 允许用户或运营人员把失败 Trace 脱敏后保存为评测候选。
- 自动提取初始环境、用户请求、关键工具、期望结果和失败证据。
- 人工确认验证器和隐私范围后进入回归集。
- 聚类重复失败，区分模型、上下文、Skill、工具、权限和程序问题。

### R22. 离线受控进化

```text
不可变运行轨迹
  → 失败聚类与根因判断
  → 生成知识/Skill/Prompt/程序候选修改
  → 回归与安全评测
  → 小范围灰度
  → 发布或回滚
```

约束：

- 生产 Agent 不直接修改可信根、验证器、权限策略和发布门槛。
- 候选修改必须保留来源、预期收益、潜在回归和回滚版本。
- 被拒绝的候选也保留记录，避免重复尝试同一失败方案。
- 评估候选本身的质量，也评估发布后是否真正被调用和遵守。

### R23. 外部 Agent / A2A 接入

支持两条路径：

1. 外部 Agent 保留原实现，通过标准协议注册为外部人才。
2. 将外部 Agent 的 Skill、知识和工具迁移为 Forge 原生资产。

接入前提：身份、权限、预算、Trace、评测、取消、数据边界和失败语义已经统一。外部 Agent 不因接入协议而自动获得可信身份。

### R24. 多模态实时工作台

候选能力包括实时语音、打断、截图理解、视觉验证、浏览器和桌面操作。只有在以下条件满足时进入规划：

- 有明确高频场景和用户群。
- 现有文本/工具方式无法满足。
- 权限、隐私、延迟和成本可以被量化控制。
- 有可自动验证的真实任务数据集。

## 12. 依赖关系与推荐顺序

```text
评测中心 ───────────────┐
Trace / 回放 ───────────┼→ 三层验证 → 失败回归 → 受控进化
                        │
状态栏 / 自动压缩 ──────┘

知识库 + 记忆 + 资产生命周期
          ↓
旗舰专家 + 用户成长路径
          ↓
多工作区团队 + 结构化交接
          ↓
连接器治理 + Automation 2.0
          ↓
ROI 看板 + 模型路由 + A2A 生态
```

建议实施批次：

1. **质量地基**：R1-R5。
2. **知识与资产**：R6-R8、R10、R13。
3. **团队生产力**：R9、R12、R17。
4. **业务系统化**：R14-R16。
5. **成本与运营**：R18-R21。
6. **长期进化与生态**：R22-R24。

## 13. 每项功能进入开发前的门槛

任何路线图项目进入“开发中”前，应具备：

1. 清晰的问题、目标用户、范围和非目标。
2. 能观察到的用户收益和至少一个成功指标。
3. 与现有 Runtime、协议、数据和权限边界的设计。
4. 失败、取消、重试、迁移和回滚方案。
5. 安全与隐私检查，尤其是记忆、连接器、自动化和跨工作区写入。
6. 评测任务、确定性验证器和回归范围。
7. Trace、指标和故障排查入口。
8. 分阶段发布与兼容策略。
9. 用户文档和运维说明。

## 14. 暂不优先投入

- 继续大量增加未经评测的通用人才模板。
- 让多个 Agent 在同一工作区自由并发写入。
- 在没有评测、灰度和回滚时允许 Agent 自动修改自身生产配置或代码。
- 只为宣传增加专家数、Skill 数、代码行数或自动化运行次数。
- 为云端化牺牲本地优先、数据所有权和离线能力。
- 没有明确产品收益的大规模模型后训练或自建基础模型。
- 没有真实场景和验证集的实时语音、桌面控制和无限层级 Agent 社会。

## 15. 维护方式

- 路线图至少在功能进入设计、开始开发、交付、暂缓或范围变化时更新。
- 进入设计的项目应链接 `docs/superpowers/specs/` 下的设计文档。
- 进入开发的项目应链接 `docs/superpowers/plans/` 下的实施计划。
- 已交付功能应补齐正式用户文档，并在路线图中简化为状态与链接，避免重复维护实现细节。
- 新功能不能只写“要做什么”，必须写清完成效果、收益、依赖和验收方法。
- 当数据证明收益不足或替代方案更好时，可以降低优先级或移出路线图，并记录原因。
